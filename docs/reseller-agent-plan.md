# 代理商（Reseller）功能 — 需求与设计规划稿

> 状态：规划稿（供讨论与排期，非可直接开发的详细设计）
> 定位：在一套已具备 **邀请返利 / 兑换码 / 订阅套餐 / 用户-分组-渠道** 能力的 new-api 系统上，规划一套「一级代理商分销」能力。
> 说明：当前代码库**不存在**现成的 reseller/代理商模块，本文为**自设计**的推荐方案，尽量复用现有能力、尽量少改动核心计费链路。

---

## 1. 背景与目标

### 1.1 现状
- 平台已有：用户管理、渠道、分组（含 `group_special_usable_group` 按用户收窄可用模型）、额度充值、支付（epay/Stripe/Creem/Waffo）、邀请返利、兑换码、订阅套餐、支付合规确认。
- **缺失**：一套让「代理商」自服务地**售卖** AI 能力给下游客户，并让平台方**监控与抽佣/结算**的完整机制。

### 1.2 目标
1. 代理商能批量创建/管理自己的下游客户，并限制其只能用授权的模型。
2. 代理商能用自己的佣金/批发余额给客户充值。
3. 平台方按下游消费（或充值）结算佣金，代理商可查看流水并申请提现。
4. 平台方可统一管控代理商、费率、结算，且不破坏现有计费与安全不变式。

### 1.3 非目标（本规划稿不覆盖）
- 多级分销（二级及以上的级差抽佣）——列为后续可选阶段。
- 代理商自行对接上游/自建渠道——代理只卖平台已有渠道，不拥有上游。

---

## 2. 角色与核心概念

| 角色 | 说明 |
|---|---|
| 平台方（root/admin） | 运营整个平台，管理渠道、分组、代理商、费率、结算审核 |
| 代理商（agent/reseller） | 从平台“批发”能力，面向下游客户；本用户体系中的一个特殊用户 |
| 下游客户（customer） | 代理商创建/发展的普通用户，通过 API Token 使用授权的模型 |

核心概念：
- **代理商（Reseller）**：一个被标记为代理商、并配置了「费率/可用模型白名单」的用户。
- **佣金（Commission）**：按下游消费（或充值）按比例给代理商记账的收益。
- **佣金余额（ResellerBalance）**：代理商可提现/用于给客户充值的钱包。
- **可用模型白名单**：平台授权给该代理商可“再售卖”的模型集合（对应平台上的渠道模型）。

---

## 3. 功能范围（推荐：一级代理分销）

### 3.1 代理商开户与配置（平台方）
- 平台在用户管理里将某用户标记为「代理商」，并配置：
  - **状态**（启用/停用）
  - **佣金比例**（按子用户消费金额的 %）
  - **批发折扣 或 成本价**（用佣金余额给客户充值的折算）
  - **可用模型白名单**（可售卖的模型集合，来自平台渠道模型）
- 平台可查看该代理商的客户数、累计佣金、待结算等。

### 3.2 下游客户管理（代理商自服务）
- 代理商创建下游客户 → 复用现有「创建用户」能力，但限定 role 为普通用户、归属到该代理。
- 代理商查看自己的下游客户列表、余额、消费明细。
- 客户归属：`customer.inviter_id`（或新增 `reseller_id`）指向代理商。

### 3.3 模型与额度限制（复用现有分组/渠道）
- 平台为代理商预设一个**专属可用模型集**。
- 代理商给客户分配模型 → 复用「专属分组 + 专属渠道 + `group_special_usable_group` 收窄」机制，让客户只能调用授权模型。
- 目的：实现「客户只能用它买的那几个模型」，既安全也便于计费。

### 3.4 佣金与结算
- **佣金成账**：按下游客户的消费日志（已结算）计算佣金，入代理商佣金余额；避免负佣金与溢出现象（沿用现有计费不变式与饱和防护）。
- **佣金用途**：代理商可提现；也可用佣金余额给客户充值（批发转售）。
- **提现/结算**：代理商发起提现申请，平台审核后线下打款（涉及支付合规与税务，规划稿按“人工审核”设计）。

### 3.5 与现有能力的复用对照表

| 现有能力 | 现状 | 在代理商方案中的角色 |
|---|---|---|
| 邀请返利（AffCode/InviterId/QuotaForInviter/Invitee） | 一次性注册奖励 | 可选：作为“归属关系”或新客奖励保留 |
| 兑换码/充值卡（redemption） | 管理员生成带额度兑换码 | 可选：代理批发买卡 → 转售给客户 |
| 订阅/会员套餐（subscription plan） | 套餐售卖 | 可选：代理售卖平台套餐 |
| 用户 / 分组 (`group_special_usable_group`) / 渠道 | 按分组/渠道路由与限制 | **核心**：代理创建客户 + 限制模型 |
| 支付渠道（epay/Stripe/Creem/Waffo）+ 合规确认 | 在线充值 | 客户充值与代理提现的支付底座 |

## 4. 新增数据模型（规划）

| 表 | 说明 | 关键字段（规划） |
|---|---|---|
| `resellers` | 代理商账户与配置 | user_id, status, commission_rate, discount_rate, model_whitelist(json), balance |
| `reseller_customers` | 代理-客户归属 | reseller_id, customer_id, created_at（或直接在 users 上加 reseller_id） |
| `reseller_commission_logs` | 佣金流水 | reseller_id, customer_id, order/consume_id, amount, rate, status(入账/冲正) |
| `reseller_withdrawals` | 提现申请 | reseller_id, amount, status(待审/通过/拒绝), audit_by/time, note |

> 规划阶段以「一级 + 简单归属」为最小集；若要做多级，再引入层级树。

## 5. 新增接口（规划）

**代理商侧（需登录代理商账号）**
- `GET /api/reseller/overview` — 我的客户/佣金/余额概览
- `POST /api/reseller/customer` — 创建下游客户
- `GET /api/reseller/customer` — 我的客户列表
- `POST /api/reseller/customer/:id/recharge` — 用佣金余额给客户充值
- `POST /api/reseller/customer/:id/model` — 设置客户可用模型（在授权白名单内）
- `GET /api/reseller/commission` — 佣金流水
- `POST /api/reseller/withdrawal` — 申请提现

**平台侧（管理员）**
- `PUT /api/reseller/:id` — 配置代理商（费率/白名单/状态）
- `GET /api/reseller/list` — 代理商列表
- `GET/POST /api/reseller/withdrawal` — 审核提现/结算

## 6. 权限与安全

- 代理商只能管理**自己下游**的客户，沿用 `canManageTargetRole` 与“只能降级/同级”约束，**不可越权**看到别的代理客户。
- 敏感操作（提现审核、费率修改、白名单授权）仅限平台方。
- 顺手沿用支付合规确认（`IsPaymentComplianceConfirmed`）作为涉及真金白银功能的门槛。

---

## 7. 计费与对账约束（沿用现有不变式）

- 佣金基于**已结算的消费 log** 计算，`序列 + 是否冲正` 保证对账一致，不重复计算。
- 佣金金额用现有 `quota` 数学工具（`QuotaFromFloat/QuotaRound/QuotaFromDecimal` 及 `*Checked` 饱和防护），**绝不产生负数/溢出**。
- 提现金额 ≤ 可用佣金余额；扣减用事务 + 行锁，避免并发超提。
- 佣金比例与折扣都有校验（0 < rate < 100% 等），非法值在入口拦截。

---

## 8. 落地分期建议

- **阶段 1（MVP，推荐先做）**
  代理商开户/配置（费率+白名单+状态）→ 代理商自建客户 → 客户模型限制（复用分组）→ 佣金按消费成账 → 佣金余额。
- **阶段 2**
  提现/结算流程（人工审核）；兑换码批发；订阅套餐的代理售卖。
- **阶段 3（可选）**
  多级分销（级差佣金）、代理自助定价、明细导出/对账报表。

---

## 9. 风险与开放问题（待讨论）

1. **佣金口径**：按「下游**消费**」还是「下游**充值**」抽佣？影响计费与资金流，需业务方拍板。
2. **合规/税务**：提现结算、发票、支付资质依赖所在地区法律；建议先走“人工审核 + 线下打款”，并确认支付合规门槛。
3. **多级复杂度**：强烈建议先做单级，多级分销的层级/返佣/防套利复杂度高，单独排期。
4. **代理商是否需要自助定价/加价**：若需要，则要引入“代理商对某模型的自定义倍率”，会与现有 `ModelRatio/GroupRatio` 计费联动，需额外设计。
5. **白名单粒度**：按模型白名单给代理，还是按“代理专属分组+渠道”，需与 3.3 方案对齐（推荐后者，安全隔离更干净）。
