# 主站发票申请、审核与开具开发文档

## 1. 目标与范围

在国内主站增加用户发票申请、管理员审核、开票信息登记、正式发票凭证下载和作废申请流程。界面参考随需求提供的截图：汇总可开金额、选择充值来源并分配金额、填写购买方信息、查看申请记录及状态。

本功能属于主站普通用户的充值财务流程，与 Agency Hub 的授信消费账单、还款和坏账功能完全分开，也不复用 `AgencyCreditInvoice`。首版只支持成功充值订单，不包含订阅、兑换码、赠送额度和模型消费。

平台当前没有税务局/电子发票服务集成。因此“开具发票”是由财务人员在外部合规税务系统真实开票后，在本站登记发票号码/日期并上传正式 PDF。本站不得自行合成或伪装税务发票；申请明细或导出表格不能称为正式发票。

## 2. 金额与来源规则

- 可开金额只能来自 `TopUp` 成功订单的 `PaymentSnapshot`，且必须同时包含正数 `ActualMoney`、`CNY` 币种和已验证支付凭证引用。
- 不以 `TopUp.Amount`（充值额度）、钱包余额、已消耗 Token、`TopUp.Money`（历史/预估金额）或模型用量推算实付金额。
- 旧订单、管理员手工补单、无实付金额/币种的支付回调及 Waffo/Waffo Pancake 等金额语义不明确的订单，不自动开放可开金额；需要后续人工核证能力时再单独设计，首版不允许前端覆盖此限制。
- 可开金额按人民币“分”使用整数保存和计算。一个申请可选择多个来源，每个来源的申请额不得大于该订单的剩余可开金额。
- `invoice_reserved_cents` 表示待审核和审核通过、尚未开票的锁定金额；`invoice_issued_cents` 表示已开票、尚未依法作废/红冲的金额。可申请余额为可信实付分额减去两者。退款/拒付与发票作废是独立财务事件，不自动改写发票记录。
- 创建申请时，在同一数据库事务内对每笔 TopUp 执行带余额上限条件的原子更新，并写入申请、来源分摊行和审计事件；任一来源失败则整个事务回滚。驳回/撤回释放锁定金额，正式开票将锁定金额转入已开票额。作废经管理员确认后才释放已开票额。

## 3. 信息与状态流程

### 申请内容

必填：购买方名称、统一社会信用代码/纳税人识别号、接收邮箱、来源订单及各自申请金额。

选填：开户银行、银行账号、购买方地址、联系电话、备注。申请时保存抬头快照，后续资料变化不能改变历史申请。

### 状态机

```text
pending_review -> approved -> issued -> void_pending -> voided
       |              |                    |
       +-> rejected                        +-> issued (作废申请驳回)
       +-> withdrawn
```

只有待审核申请可由用户撤回；待审核申请可由管理员通过或驳回，驳回必须填写原因。已通过申请仍未代表正式开票，财务须录入真实发票号码、开票日期并上传正式 PDF 才能转为 `issued`。已开票用户可申请作废，管理员必须确认真实作废/红冲已在外部税务系统处理后才可确认作废，否则驳回并恢复为 `issued`。不物理删除申请、发票或事件记录。

所有状态变化追加写入不可变事件记录（操作者、角色、动作、前后状态、原因、时间）。邮件发送失败不回滚真实开票状态；记录发送结果并允许管理员重发。

## 4. 数据模型

- `InvoiceApplication`：申请号、用户、状态、购买方信息快照、总申请分、币种、审核原因/人员/时间、发票号码/日期、邮件发送状态、创建/更新时间。
- `InvoiceApplicationLine`：申请 ID、TopUp ID、订单号快照、来源实付分额快照、申请分额；同一申请不可重复添加同一充值来源。
- `InvoiceApplicationEvent`：不可变的申请生命周期事件、操作者和原因。
- `InvoiceApplicationDocument`：正式发票 PDF 的内容、大小、MIME、SHA-256；与申请分表，避免普通 API 查询读取文件字节。
- `TopUp` 增加仅供服务端使用的 `invoice_reserved_cents` 和 `invoice_issued_cents` 计数列（JSON 隐藏，默认零）。

新模型加入主库完整与快速迁移路径。表关系使用 GORM 常规字段/索引，不使用方言专属类型、SQL 或依赖 SQLite 不支持的行锁语法。
正式发票号码按去除首尾空白、大小写不敏感的摘要建立唯一键；同一号码不能登记到多个申请。号码摘要只供唯一性校验，不向接口返回。

## 5. 权限、安全与隐私

- 用户端接口要求登录；列表、详情、撤回、作废申请和凭证下载均由服务端按当前用户 ID 限定。不可根据客户端提交的 `user_id` 授权。
- 管理端审核/开票/作废/重发接口统一要求 `AdminAuth`。敏感管理动作写入生命周期事件和管理审计日志；管理列表默认不返回纳税识别号、银行账号或文件内容，详情按需展示。
- 上传仅接受大小不超过 10 MiB、内容签名与 MIME 一致的 PDF。拒绝路径、脚本、任意 HTML/SVG、空文件和伪装扩展名。以固定服务端文件名作为邮件附件名，不信任客户端文件名。
- 文件作为私有数据库内容存储，适用于主库双实例共享；不放入 Web 静态目录、不返回对象存储公开 URL。下载必须检查用户归属或管理员角色、发票已开具、响应使用 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff` 和附件下载头。
- 表单和错误均由服务端二次校验；用户/管理员接口禁用缓存并限制申请/上传请求体。日志不得包含完整税号、银行账号、邮件正文或发票二进制。
- 正式开票后向申请邮箱发送正式 PDF 附件；发送状态单独记录，发送失败可重试，不影响用户在本站下载。
- 开票日期必须是非未来的有效时间戳；服务端始终根据 PDF 字节重新计算 SHA-256，不信任客户端摘要。开票与作废理由最多 1000 个字符，发票号码最多 128 个字符。
- “重发邮件”仅适用于已开票或待作废审核状态；成功和失败均写入管理审计事件，不记录邮箱、邮件正文或文件内容。

## 6. API 草案

用户接口统一置于 `/api/invoice-applications`，要求登录并禁用缓存：

- `GET /summary`：可开、审核中、已开票金额汇总。
- `GET /sources`：当前用户具有可信 CNY 支付事实的充值来源及剩余可开金额；仅返回必要的订单标识和日期，不暴露支付引用。
- `GET /`、`GET /:id`：当前用户申请列表/详情。
- `POST /`：提交抬头快照及来源分摊。
- `POST /:id/withdraw`：撤回待审核申请。
- `POST /:id/void-request`：对已开票记录申请作废。
- `GET /:id/document`：仅申请人且正式开票后可下载。

管理员接口置于 `/api/invoice-applications/admin`，要求 `AdminAuth`：

- `GET /`、`GET /:id`：审核队列及详情。
- `POST /:id/review`：通过或驳回；驳回必须填写原因。
- `POST /:id/issue`：多部分表单，登记真实发票号码、日期、开票金额（`amount_cents`，必须等于申请总额）并上传 PDF；PDF 的 MIME、文件名和 SHA-256 由服务端确定。
- `POST /:id/void-review`：确认已在外部税务系统作废/红冲，或驳回作废申请；均需原因。
- `POST /:id/resend`：重发正式发票邮件。
- `GET /:id/document`：管理员下载已开具凭证。

响应 DTO 不直接序列化 GORM 模型、支付快照或文件字节。列表使用项目分页契约，所有金额以整数分在 API 内传输并由页面格式化为人民币元。

## 7. 前端页面

- 用户页 `/invoices`：个人侧栏入口；顶部展示可开、审核中、已开票金额；左侧列出可开充值来源并输入分摊金额，右侧显示汇总和提交按钮；表单包含截图中的购买方必填/选填字段；记录列表支持状态筛选、详情、撤回、作废申请及已开票凭证下载。
- 管理页 `/invoice-review`：管理员侧栏入口；显示待审核、待开票和待处理作废队列；详情中核对购买方、分摊来源和金额；分别执行审核、上传正式发票及处理作废申请。
- 路由本身增加 `ROLE.ADMIN` 前端守卫，但后端鉴权才是授权最终边界。React Query 变更后失效相关列表和汇总缓存；所有可见文案进入 i18n。复用项目已有 Button、Input、Form、Dialog/Sheet、StatusBadge、EmptyState、分页/表格和主题 token。
- 侧栏需同步默认配置、URL 映射、管理员可配置项及个人侧栏配置，保持旧配置兼容。

## 8. 验收与验证

1. 只有成功且具备有效正数 CNY 实付快照的充值来源可申请；余额/额度、旧 `Money`、免费订单和未知支付凭证不能增加可开金额。
2. 同一充值来源并发提交或重复请求不会导致锁定额与已开票额超过实付金额；用户不能跨账号读写申请或下载文件。
3. 状态机拒绝非法跳转；审核驳回、用户撤回、正式开票、作废申请、作废驳回/确认、邮件失败及重发均留下事件记录。
4. PDF 类型伪装、超限、空文件和未开票下载被拒绝；有效 PDF 仅由授权用户下载且响应不缓存。
5. 后端增加金额解析、余额边界（包括负数计数与 int64 溢出）、状态竞态/并发、发票号码唯一性、所有权、下载与上传校验测试；前端增加金额分摊、校验、禁用/加载、筛选及状态操作交互测试。
6. 新迁移在 SQLite、MySQL、PostgreSQL 的真实实例分别验证新库、从当前发布版结构升级、连续运行迁移两次及数据/索引保留。SQLite 的本地测试可运行；当前无 MySQL/PostgreSQL 测试 DSN，因此这两项需有对应测试实例后才能宣称已验证。
7. 执行受影响 Go 测试和构建、前端目标测试、`bun run typecheck`、涉及文件 lint、i18n 检查、格式检查和 `git diff --check`。不连接生产环境、不部署、不推送、不提交。
