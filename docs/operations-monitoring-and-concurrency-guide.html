一次请求会采集什么

入口中间件

记录请求 ID、节点名、开始时间、HTTP 方法、路径和端点类型；请求完成后计算总耗时和下游状态码。

Relay 元数据

补充用户 ID、Token ID、客户模型、实际上游模型、分组、渠道、渠道类型、渠道密钥索引、流式标记和任务 ID。

上游用量

规范化为互不重叠的输入、输出、缓存读取、缓存创建四类 Token；失败请求的 Token 不进入概览 Token 汇总。

错误和尝试

记录错误归属、有效状态码、脱敏摘要、重试索引、账号切换和每次上游尝试的耗时与并发等待时间。

隐私边界：观测表不保存请求正文和响应正文。错误摘要会先脱敏并限制预览长度；原始记录中的内部 ID 和错误摘要仅通过 Root 接口查看。

4. 统一统计口径

以下符号用于后续全部公式。业务请求指标会先应用对应筛选条件和时间窗口，再进行计算；实时并发、后台任务和固定 30 天模型速度等区域的筛选边界见第一节。

符号含义来源
R观测请求总数request_count
S成功请求数HTTP 2xx/3xx 且没有记录业务错误码
E失败请求数E = R - S
B业务限制失败数本地配额、鉴权、非法请求、本地并发限制等
FSLA 错误数F = E - B
U上游错误数归属 provider、状态码 ≥400，并排除 429/529
I/O/CR/CC输入 / 输出 / 缓存读取 / 缓存创建 Token仅成功请求参与概览汇总
T总 TokenT = I + O + CR + CC
W选择窗口秒数end - start
effective_status = upstream_status_code > 0 ? upstream_status_code : downstream_status_code success = (200 ≤ downstream_status_code < 400) AND error_code 为空 E = R - S F = E - B U = provider_error AND effective_status ≥ 400 AND effective_status NOT IN (429, 529)

未进入 Relay 的鉴权失败也会被入口中间件记录。例如下游 401 会被归属为 gateway 并标记为业务限制，因此不降低 SLA。未显式分类的失败默认归属 gateway；400、401、403、429 默认视为业务限制。

业务限制的判定

仅当错误归属为 gateway 时，本地配额不足、预扣费失败、模型价格错误、非法请求、请求体错误、访问拒绝、无法取得渠道，以及错误码中包含 quota 或 concurrency 的错误会进入 B。provider 返回的 429/529 不属于本地业务限制，仍会降低 SLA，但不会进入上游错误率的分子。

5. 请求、Token、QPS/TPS

概览指标

总请求数 = R 成功请求数 = S 总错误数 = E = R - S 业务限制数 = B SLA 错误数 = F = E - B 上游错误数 = U SLA = S / (S + F) 请求错误率 = F / (S + F) 上游错误率 = U / (S + F) 平均 QPS = R / W 平均 TPS = T / W 平均账号切换数 = Σswitch_count / R

当 S + F = 0 时，SLA 和两个错误率返回 0；页面在没有请求时通常显示为待机。只要分母存在，SLA + 请求错误率 = 100%。

示例：窗口内 R=1000、S=950、B=30，则 F=20，SLA=950/(950+20)=97.938%，请求错误率=2.062%。如果其中 U=15，上游错误率=15/970=1.546%。

Token 规范化

语义输入输出缓存读取缓存创建
OpenAI / 通用InputTokens，为 0 时使用 PromptTokens，再减去缓存读取和缓存创建OutputTokens，为 0 时使用 CompletionTokens取两套 details 中较大的 cached tokens取 details 和 Claude 5m/1h 分拆中的较大值
Anthropicinput_tokensoutput_tokenscache_read_input_tokens所有 cache creation 子项合计
Geminiprompt_token_count - cached_content_token_countcandidates_token_countcached_content_token_count0

所有规范化分量都做非负保护。总 Token 四项互斥，避免缓存 Token 既算普通输入又算缓存用量。

当前值、峰值与趋势

当前 QPS = 最近 60 秒请求数 / 60 当前 TPS = 最近 60 秒成功请求 Token / 60 峰值 QPS = max(每个自然分钟请求数 / 60) 峰值 TPS = max(每个自然分钟 Token 数 / 60)
  • 只要窗口仍在原始数据保留期内，“当前值”直接查询原始事件的最后 60 秒。
  • 历史窗口超出原始保留期时，当前值由分钟表近似，接口将 approximate=true。
  • 峰值是“最高自然分钟的平均速率”，不是单秒峰值；窗口首尾不足一分钟仍除以 60。
  • 趋势桶宽：窗口 ≤2 小时为 60 秒；≤24 小时为 300 秒；更长为 3600 秒。
  • 趋势补齐空桶；每个点的 QPS/TPS 始终除以完整桶宽，因此不完整边缘桶可能偏低。

6. 延迟与 TTFT

请求总耗时和 TTFT 只统计成功请求；TTFT 只统计有首个流式响应时间的样本。

duration_ms = completed_at - request_started_at TTFT_ms = first_response_time - relay_start_time Avg = Σ样本值 / 样本数 Max = max(样本值)

精确百分位

窗口位于原始保留期内且成功请求不超过 50,000 条时，后端读取全部样本、升序排列并线性插值：

position = (n - 1) × p lower = floor(position) upper = ceil(position) Pp = round(values[lower] + (values[upper] - values[lower]) × 小数部分)

分别计算 P50、P90、P95、P99，平均值采用整数除法。接口返回 approximate=false。

分钟聚合近似百分位

窗口超出原始保留期或样本超过 50,000 条时，使用分钟表中的六档直方图估算：

档位边界规则
0–100msvalue < 100
100–200ms100 ≤ value < 200
200–500ms200 ≤ value < 500
500–1000ms500 ≤ value < 1000
1000–2000ms1000 ≤ value < 2000
2000ms+value ≥ 2000

先定位目标累计样本所在档位，再按该档内部样本比例做线性估算；最后一档的上界使用窗口最大值。此时 approximate=true。延迟直方图只展示总耗时档位，TTFT 仍返回独立的百分位摘要。

7. 错误、SLA、重试与账号切换

错误趋势和分布

错误趋势按趋势桶分别展示 SLA 错误 F、上游错误 U 和业务限制 B。错误分布按有效状态码聚合，每个状态码同时返回总错误、SLA 错误、业务限制和上游错误，最后只保留总错误数最多的 20 个状态码。

状态码分布键 = effective_status TopStatusCode = Top 20 中 total 最大的状态码 同 total 时按状态码升序

错误归属

  • 网络请求失败、读取上游响应失败、上游坏状态/坏响应/空响应、AWS 调用错误等归属 provider。
  • new-api 自身校验、配额、价格、路由和鉴权错误默认归属 gateway。
  • 异步任务错误中，LocalError=true 归属 gateway，否则归属 provider。
  • 错误摘要保存前调用敏感信息遮罩；详情页按请求 ID 同时展示请求和全部上游尝试。

重试和账号切换

账号身份由 (channel_id, key_index) 组成。一次下游请求第一次使用某个账号不算切换；后续遇到此前未见过的账号才增加一次切换。回到已经见过的账号不会再次增加切换数。

switch_count(request) = 本请求中“首次出现的新账号（排除第一个）”数量 平均账号切换数 = Σswitch_count / R retry_count = RelayInfo.RetryIndex 的请求级累计值

每次上游 attempt 还会独立保存 attempt 索引、渠道、密钥、耗时、状态、错误码、是否切换、并发等待毫秒数和是否被并发追踪。

8. 视频任务生命周期与模型 Token 速度

视频任务生命周期

提交数 = endpoint_type=video_submit 的请求数 提交成功数 = 上述请求中的成功数 提交成功率 = 提交成功数 / 提交数 终态任务数 = SUCCESS + FAILURE 生成成功率 = SUCCESS / 终态任务数 排队时间 = start_time - submit_time 生成时间 = finish_time - start_time 端到端时间 = finish_time - submit_time

submit_time 缺失时使用 created_at；数据库中大于 1012 的时间戳按毫秒转为秒。只有时间顺序有效的样本才进入相应平均值。任务状态来自统一 tasks 表，而不是请求日志推断。

筛选差异：“提交数/提交成功数”来自已经应用页面模型、分组、渠道、端点和节点筛选的请求聚合；“终态、生成成功率、排队/生成/端到端耗时”当前只按任务 created_at 时间范围查询，不携带上述业务筛选。

模型 Token 速度

该卡片当前固定查询最近 30 天、模型名以 gpt 开头的成功请求，并以自然分钟为缓存键；它不跟随页面顶部的 5m/1h/24h 窗口和模型/渠道筛选。

单请求输出速度_i = output_tokens_i × 1000 / duration_ms_i 平均 Tokens/s = AVG(单请求输出速度_i) 条件：duration_ms > 0 AND output_tokens > 0 平均 TTFT = AVG(ttft_ms WHERE has_ttft=true) 平均耗时 = AVG(duration_ms) 输出 Token 总数 = SUM(output_tokens)

这是“每请求输出速度的算术平均”，不是 Σoutput_tokens / Σduration，也没有从总耗时中扣除 TTFT。

后台任务心跳

按系统任务类型读取最近 1000 条任务：最新失败时间晚于最新成功时间时为 failed；异步任务轮询和 Midjourney 轮询在最后成功超过 15 分钟时为 stale；其余为 healthy。

10. 综合健康分与智能诊断

健康分将业务质量与基础设施组合为 0–100 分；诊断提示另有可配置阈值和少量固定阈值。

通用线性降分函数

L(x; healthy, critical) = 100 , x ≤ healthy 0 , x ≥ critical (critical - x)/(critical - healthy)×100, 其他

业务分

ErrorPct = 100 × max(请求错误率, 上游错误率) ErrorScore = L(ErrorPct; 1, 10) TTFTScore = 100 , 没有 TTFT 样本 TTFTScore = L(TTFT_P99_ms; 1000, 3000) , 有样本 BusinessHealth = 0.5 × ErrorScore + 0.5 × TTFTScore

基础设施分

StorageScore = 0 , 任意节点 DB 不健康 StorageScore = 50 , DB 均健康，但任意启用 Redis 的节点不健康 StorageScore = 100 , 其他 NodeCompute = [L(CPU%; 80, 100) + L(Memory%; 85, 100)] / 2 ComputeScore = min(所有节点 NodeCompute) JobScore = 100 × (1 - 非 healthy 任务类型数 / 任务类型总数) InfraHealth = 0.4 × StorageScore + 0.3 × ComputeScore + 0.3 × JobScore

最终分数

Health = round(0.7 × BusinessHealth + 0.3 × InfraHealth) Health ≥ 90 → healthy 60 ≤ Health < 90 → warning Health < 60 → critical

展开后的权重约为：错误 35%、TTFT 35%、存储 12%、计算 9%、后台任务 9%。当窗口内 完全没有观测请求 时，代码直接返回 idle / 100，此时基础设施异常不会降低该综合分，但仍会出现在独立系统卡片和诊断列表中。

智能诊断触发条件

界面统一颜色规则

  • 灰色 neutral：无样本、未知、未启用或仅观察模式。
  • 蓝色 info：请求量、吞吐、绝对并发数、网络速率和无告警阈值的耗时等纯信息指标。
  • 绿色 success：健康、可用、零失败或处于正常阈值范围。
  • 黄色 warning：接近阈值、部分可用、发生排队或渠道切换等需要关注但仍可恢复的状态。
  • 红色 critical：达到严重阈值、服务不可用、任务失败、5xx 或遥测数据丢弃。

所有“越低越好”的可配置指标统一在达到严重阈值的 80% 时变黄、达到阈值时变红；SLA 等“越高越好”的指标低于阈值变红，阈值以上 0.1 个百分点以内变黄。HTTP 4xx 显示黄色，5xx 和无有效状态码显示红色；趋势图的多序列颜色只用于区分数据系列，不代表健康状态。

11. 并发观测、排队、租约与可用性

并发模块在全局执行关闭时仍建立短期租约以展示真实占用；只有全局执行和匹配规则同时开启时才限制请求。

生效条件

enforce = concurrency_enforcement_enabled AND 找到匹配规则 AND rule.enabled AND rule.max_concurrency > 0

规则匹配先查精确的渠道密钥索引，再回退到该渠道的“全部密钥”规则（key_index=-1）。精确规则即使处于 disabled，也会遮蔽全部密钥规则，因此如需恢复继承，应删除精确规则，而不只是把它关闭。

Redis 模式

  • 占用和等待队列使用 Redis ZSET；score 为租约到期毫秒或进入队列时间。
  • Lua 脚本先清理过期租约，再按等待队列排名和剩余容量原子授予名额。
  • 排队时每 100ms 重试一次；队列已满或超时返回 HTTP 429、错误码 concurrency_limit，并跳过自动重试。
  • 租约每 lease_seconds / 3 自动续期；请求结束时主动从渠道、密钥和用户维度释放。
  • Redis 让多个 new-api 实例共享同一套并发容量，是生产多实例部署的推荐方式。

本地模式与 Fail Open

  • 未启用 Redis 时，使用进程内计数器和 50ms 轮询；限制只对当前实例有效，不能形成集群总上限。
  • Redis 已启用但命令发生错误时：若执行开启且 fail_open=false，请求返回错误；若 fail_open=true，记录错误并退回本地“只观测”，不因规则拒绝。
  • fail_open 不代表“Redis 未配置时不限制”。Redis 完全未启用时，代码会采用本地规则执行。

并发指标

渠道负载率 = in_use / capacity × 100% 平台负载率 = Σ渠道 in_use / Σ渠道 capacity × 100% 分组负载率 = Σ渠道 in_use / Σ渠道 capacity × 100% 可用率（可由返回字段计算） = available_channels / total_channels × 100%

平台按渠道类型聚合；一个渠道属于多个分组时，会完整贡献给每个分组，因此不同分组不能再次相加。用户并发只列出当前存在租约的用户，并按占用数降序。

并发快照字段

字段含义
enforcement_enabled全局并发执行开关的当前值。
redis_backed当前实例是否使用 Redis 共享租约；false 表示进程内观测/限制。
in_use尚未释放且未过期的渠道租约数。
capacity根据 enabled 的全部密钥或逐密钥规则计算的展示容量。
waiting匹配规则当前等待者数量合计。
load_percentin_use/capacity×100%；capacity=0 时为 0。
limit_configured该渠道是否存在任何规则记录，包括 disabled 规则。
limit_enabled是否至少存在 enabled 且容量大于 0 的规则。
available渠道状态、运行时冷却和容量检查后的可调度判断。
unavailable_reasondisabled、rate_limited、overloaded、temporarily_unschedulable 或 at_capacity。

渠道可用性判定顺序

  1. 渠道状态不是 enabled：disabled。
  2. 最近一次 attempt 返回 429，且冷却未结束：rate_limited。
  3. 最近一次 attempt 返回 529，且冷却未结束：overloaded。
  4. 最近一次 attempt 返回其他 ≥500，且临时冷却未结束：temporarily_unschedulable。
  5. 启用的并发容量已满：at_capacity。
  6. 以上均不满足：available。

运行时 429/529/5xx 冷却标记只写 Redis。没有 Redis 时不会跨请求保存这三类可用性状态。

12. 全局设置项：意义、默认值和范围

界面中的百分比以 0–100 展示；REST API 中对应值使用 0–1，例如 99.5% 发送为 0.995。

字段默认允许范围意义与建议
enabledtrue布尔控制请求入口观测和系统资源采集。关闭不会删除历史数据；并发控制是独立开关。

system_retention_days901–3650 天系统、网络、DB、Redis 指标保留期。
system_collection_interval_secs6015–3600 秒每实例采集间隔。小于 60 秒不会产生多个分钟点，只会覆盖同一分钟最新值。

enabled=false 的当前边界：入口请求事件和系统指标停止新增，但上游 attempt 集成点仍可能为了并发占用、切换和错误诊断写入 attempt 记录。它不是“彻底停止所有运维表写入”或“清空历史数据”的开关。

13. 渠道并发规则设置

规则保存在独立表中。配置规则本身不会立即限流；必须同时开启全局并发执行。

字段范围意义
channel_id>0 且渠道存在规则所属渠道。
key_index-1 或 0…multi_key_size-1-1 表示渠道全部密钥；非负值只约束指定密钥。未传时按 -1。
enabled布尔该规则是否允许参与执行；全局开关仍优先。
max_concurrency0–100000并发容量。规则 enabled 时必须大于 0。
queue_size0–100000容量满后最多允许多少个等待者。0 表示不排队，满载立即拒绝。
queue_timeout_ms0–3600000ms最大等待时间；0 在运行时使用 30 秒默认等待。
lease_seconds0–86400 秒0 表示继承全局 default lease；大于 0 时覆盖。

容量展示规则

  • 存在 enabled 的“全部密钥”规则时，渠道展示容量等于该规则的 max_concurrency。
  • 没有 enabled 的全部密钥规则时，渠道展示容量为所有 enabled 密钥规则容量之和。
  • 没有任何 enabled 规则时容量为 0、负载率为 0，但仍可展示只观测得到的 in-use。
在多实例生产环境正式开启限制前，应确认 Redis 正常，并根据上游真实账号配额选择作用域。没有 Redis 时，每个实例都拥有自己的本地容量，例如两台实例各设 10，集群实际可能达到 20。

14. 设置方法：管理界面与 Root API

通过管理界面

  1. 使用 Root 账号登录新版管理界面。
  2. 进入 系统信息 → 运维监控。
  3. 切换到 设置 标签页。
  4. 先调整观测、保留期、采集间隔和诊断阈值，点击“保存设置”。
  5. 在“渠道并发限制”中选择渠道、全部密钥或指定密钥，填写容量、队列、超时和租约，保存规则。
  6. 观察并发页面一段时间；确认容量合理后，最后再打开“并发限制执行”。

全局设置保存到主数据库 options 表，当前实例立即更新；其他实例通过系统选项同步周期加载，默认同步频率为 60 秒。并发规则保存后当前实例立即刷新，所有实例还会每 30 秒重新加载规则。

15. 推荐上线顺序与排障方法

安全启用并发限制

  1. 只观测：保持全局 enforcement=false，运行至少一个业务峰值周期。
  2. 确定容量：查看渠道 in-use 峰值、上游 429/529、延迟和成功率，并结合供应商官方并发限制。
  3. 先建规则：为单个低风险渠道建立规则，queue size 先设较小值，fail open 保持 true。
  4. 确认 Redis：多实例环境检查 Redis healthy、连接池和 Redis-backed 标记。
  5. 开启总开关：在低流量时段打开 enforcement，观察 429 concurrency_limit、等待时间和队列。
  6. 逐步扩展：确认无误后再增加其他渠道；严格保护供应商时可评估 fail open=false。

常见现象

页面没有请求数据

检查 enabled、查询时间窗口、端点是否在分类范围、筛选条件是否过窄；再查看 telemetry 队列是否出现 dropped。非公开 API 和管理页面本来就不进入请求观测。

系统指标有多条节点曲线

这是正常的逐实例采集。检查每个实例的 NODE_NAME 是否唯一；Blue/Green 不应复用相同节点名，否则同一分钟会互相覆盖。

当前 QPS 与峰值 QPS 感觉偏低

当前值是最后 60 秒平均，峰值是最高自然分钟平均，不是瞬时单秒峰值；历史窗口或不完整边缘分钟还可能使用近似值。

设置规则后没有拒绝请求

检查全局 concurrency_enforcement_enabled 是否仍为 false、规则是否 enabled、max concurrency 是否大于 0，以及精确密钥规则是否遮蔽了全部密钥规则。

多实例并发超过设置值

确认页面显示 Redis-backed。没有 Redis 时容量按实例独立计算；两台实例各限制 10，集群可能达到 20。

SLA 很高但总错误数不低

SLA 排除了业务限制 B。鉴权、客户配额、非法请求和本地并发限制可能增加总错误，但不进入 SLA 分母。

健康分 100，但 DB/Redis 有告警

窗口没有请求时健康分直接返回 idle/100；基础设施告警仍会独立展示。此时应以系统卡片和诊断项为准。

16. 精度、范围和当前实现边界

  • 不是全站访问日志：只观测被分类的公开 AI、任务、视频、素材和认证端点。
  • 失败 Token 不计入概览：即使上游在失败前消耗了 Token，当前总 Token 仍只累加成功请求。
  • 原始与聚合精度不同：原始保留期内概览为精确请求聚合；延迟仅在 ≤50,000 样本时精确，其他情况按六档近似。
  • 最大查询窗口 31 天：更早历史可以保留在分钟表，但单次 Dashboard 快照会把 start 收窄到 end 前 31 天。
  • 模型速度卡片固定口径：最近 30 天、gpt% 模型，不随主筛选变化。
  • 平台/分组容量不可交叉求和：同一渠道可属于多个分组。
  • 本地并发不是集群并发：生产多实例需要 Redis 才能共享租约。
  • 可用性冷却依赖 Redis：没有 Redis 时 429/529/5xx 不形成跨请求冷却状态。
  • 配置同步有传播时间：其他节点的全局设置通常在选项同步周期内生效；并发规则最长约 30 秒刷新。
  • NODE_TYPE 不控制 HTTP 流量：它决定迁移和部分后台任务；Caddy Blue/Green 权重与运维任务执行实例互相独立。
实现原则：观测数据不参与客户扣费；并发限制在默认状态下不改变业务流量。先用真实数据建立基线，再把控制能力逐渠道打开。
