# Distributor 代理商分销服务需求文档

## 0. 文档信息

| 项目 | 内容 |
|---|---|
| 文档状态 | 需求评审稿 |
| 英文名称 | Distributor |
| 产品定位 | 在现有 Token 平台旁建设一级代理商分销服务 |
| 核心对象 | 平台、代理商、代理商邀请的真实注册用户、可返佣额度批次、模型消费、佣金、提现 |
| 一期口径 | 充值只建立可返佣额度资格；模型调用完成最终结算后，按实际消费实时产生佣金 |
| 架构约束 | 模型请求仍直接进入现有网关，Distributor 服务不进入 `/v1/*` 模型调用链路 |
| 改造边界 | 一期不是完全零核心改动；充值结算和最终计费点必须可靠写出 Distributor 服务可消费的本地事实事件 |

本文描述业务需求和验收口径，不作为数据库 DDL 或接口字段的最终详细设计。文中“金额”均指法币金额，必须使用定点数或最小货币单位保存，不使用浮点数参与结算。

## 1. 背景与目标

平台已有用户注册、邀请码、用户归属、充值订单、Token、额度和消费日志能力。现在需要为通过平台销售 Token 的代理商提供独立的获客、定价、业绩、佣金和提现能力。

一期目标：

1. 平台管理员能够开通、停用和配置代理商。
2. 代理商能够设置对客户展示的销售折扣，并获得对应邀请链接和二维码。
3. 新客户通过邀请链接或二维码进入注册流程，注册成功后自动且唯一地归属于该代理商。
4. 归属客户充值时按代理折扣获得可返佣额度，实际调用模型并完成结算后实时形成业绩和佣金。
5. 代理商登录后能够查看可提现金额、累计入账佣金、业绩明细、佣金流水和提现记录。
6. 平台管理员能够审核提现、处理冲正，并完成财务对账和审计。
7. Distributor 服务故障不影响已有客户调用模型 API。

## 2. 一期范围与非目标

### 2.1 一期范围

- 一级代理商，不支持代理商发展下级代理商。
- 代理商使用现有平台账号登录，不建立第二套密码体系。
- 客户是现有平台中的真实注册用户，可正常登录、充值和创建 Token。
- 一个客户只能归属一个代理商。
- 佣金按每次模型调用的最终实际消费计算；预扣费、充值到账和未消费余额均不产生佣金。
- 充值订单建立可返佣额度批次，用于限制累计返佣不超过客户真实付费购买且未退款的额度。
- 提现采用“申请、人工审核、线下打款、平台确认”的流程。
- 邀请链接、二维码、客户归属、佣金、提现和审计由 Distributor 服务提供。
- 复用现有平台的邀请码和 `users.inviter_id` 完成零核心改动的基础归属。

### 2.2 一期不做

- 多级分销、团队级差、区域代理。
- 代理商自有域名、独立品牌站和独立支付商户。
- 自动打款、自动开票、税务代扣。
- 代理商修改平台模型定价、渠道、模型倍率或上游密钥。
- 对预扣费立即返佣；只有最终结算消费才允许入佣。
- 已注册用户自行改绑代理商。
- 同一代理商为不同客户配置不同销售折扣。
- 邀请链接携带多个并行活动价。需要多活动价时在后续版本引入活动维度。

## 3. 角色与权限

| 角色 | 数据范围 | 主要权限 |
|---|---|---|
| 平台超级管理员 | 全平台 | 开通代理商、配置结算规则、审核提现、冲正、查看全量报表和审计 |
| 平台财务 | 全平台财务数据 | 审核和确认打款，不得修改渠道和系统配置 |
| 代理商管理员 | 本代理商 | 设置销售折扣、管理邀请入口、查看客户和业绩、申请提现、维护收款信息 |
| 代理商只读成员 | 本代理商 | 查看概览、客户、业绩、佣金和提现记录 |
| 客户 | 本人 | 注册、充值、使用 Token；不得访问代理商后台 |

代理商账号推荐使用现有普通用户身份，再由 Distributor 服务授予代理商角色。若绑定现有平台管理员账号，该账号仍保留原平台的全局权限，不能视为完成了代理商数据隔离。

### 3.1 如何指定一个平台账号为代理商

“平台账号”和“代理商”是两个不同对象，不能通过修改现有 `users.role` 来表示代理商：

```text
现有 users.id（登录身份）
        |
        v
distributor_memberships（授权关系）
        |
        v
distributor_accounts（代理商业务主体）
```

平台超级管理员在 Distributor 管理后台执行以下操作：

1. 按用户名、邮箱或用户 ID 查找一个已启用的现有平台账号。
2. 创建代理商业务主体，填写代理商名称、状态、结算折扣、销售折扣范围、返佣事件规则等信息。
3. 将选中的平台账号写入 `distributor_memberships`，角色设为 `distributor_admin`。
4. 将该账号设为代理商主账号 `owner_user_id` 和一期邀请身份 `invite_user_id`。
5. 创建成功后，该用户继续使用原平台账号和密码登录；进入 `/distributor/` 时，Distributor 服务根据当前 `users.id` 查询有效成员关系，确定其 `distributor_id` 和代理商角色。

一期约束：

- 一个现有平台账号只能加入一个代理商。
- 每个代理商必须且只能有一个主账号，但可以增加只读成员或其他代理商管理员。
- 新增成员只获得后台操作权限，不自动获得新的对外邀请码。
- 客户归属属于代理商业务主体，不属于某个后台操作员；更换主账号不能改变历史客户归属、佣金或提现记录。
- 代理商主账号建议使用普通用户角色。Distributor 服务角色不改变该账号在现有平台中的 `users.role`。

### 3.2 代理商信息在哪里管理

代理商业务信息统一在 Distributor 管理后台的“平台管理 -> 代理商管理”中维护，不塞入现有用户表：

| 信息 | 权威数据源 | 管理位置 |
|---|---|---|
| 用户名、邮箱、密码、账号启停 | 现有平台 `users` | 现有平台用户管理 |
| 代理商名称、编号、业务状态 | `distributor_accounts` | Distributor 管理后台的代理商管理 |
| 主账号和操作员权限 | `distributor_memberships` | Distributor 管理后台的成员管理 |
| 平台结算折扣、销售折扣区间、返佣规则 | `distributor_accounts` 和折扣版本表 | Distributor 管理后台的定价配置 |
| 邀请链接、二维码和邀请状态 | `distributor_invite_links` | Distributor 管理后台的邀请推广 |
| 客户归属 | `distributor_customer_bindings` | Distributor 管理后台的客户管理；仅平台可迁移 |
| 佣金、余额和提现 | 佣金、钱包账本、提现表 | Distributor 管理后台的财务管理 |
| 收款账户 | `distributor_payout_accounts` | 代理商维护、平台审核 |

现有平台后台可以提供“进入代理商管理”的跳转和代理商标识，但代理商配置的增删改查应由 Distributor 服务接口完成，避免把代理商财务权限扩散到现有全局管理员接口。

## 4. 核心业务定义

### 4.1 折扣定义

统一使用“销售折扣率”，避免“打几折”和“优惠百分比”混淆。销售折扣决定客户购买同等标准额度需要支付的金额：

```text
客户应付金额 = 平台标准售价 × 客户销售折扣率
```

示例：平台标准售价为 100 元，代理商设置 90%（九折），客户应付 90 元。

系统内部使用基点 `BPS` 保存比例：10000 表示 100%，9000 表示 90%。界面同时显示“90% / 九折”。

### 4.2 佣金定义

仅有“代理商对外折扣率”无法计算佣金，平台还必须为每个代理商配置“平台结算折扣率”。每次调用以最终结算的实际消费额度计算，而不是以充值金额或预扣额度计算。

```text
本次标准消费金额 V = 最终实际消费 quota / QuotaPerUnit
本次客户销售金额 = V × 该额度批次的销售折扣率
本次平台结算成本 = V × 该额度批次的平台结算折扣率
本次代理商佣金 = max(0, 本次客户销售金额 - 本次平台结算成本)
```

`V` 先按平台计费基准币种计算；如代理商钱包使用人民币等展示币种，必须使用消费批次中冻结的汇率快照转换，不能按提现当天汇率回算。

示例：某批额度按销售折扣 90%、平台结算折扣 80% 购入。客户最终实际消费了标准价值 10 元的额度，本次客户销售业绩为 9 元，平台结算成本为 8 元，实时佣金为 1 元。客户账户中尚未消费的额度不产生佣金。

业务约束：

- `平台结算折扣率 <= 客户销售折扣率 <= 平台允许的最高折扣率`。
- 平台可为代理商配置最低和最高销售折扣范围，代理商只能在范围内设置。
- 折扣变更只影响变更生效后的新可返佣额度批次，不改变已有额度批次的利润空间。
- 充值成功时快照销售折扣、平台结算折扣、获赠额度和支付订单；消费时按 FIFO 分配到可返佣额度批次。
- 新用户赠送、普通邀请奖励、管理员赠送、兑换码和订阅额度默认不建立可返佣批次，不能产生代理佣金。
- 同一笔消费的累计返佣额度不得超过其最终实际消费额度，同一客户的累计返佣额度不得超过其净可返佣额度批次总量。
- 预扣事件不得产生佣金。同步请求以 `settle/postconsume` 最终值为准，异步任务以成功终态或最终差额结算值为准。
- 负向消费调整和任务退款通过原消费记录的反向流水冲正，不能生成一笔无来源的负佣金。
- 佣金金额不得因异常参数或算术溢出变成负数；额度和金额转换必须使用统一的定点数及饱和检查。

### 4.3 可返佣额度批次

按消费返佣仍需要记录客户的真实付费来源，否则客户消费注册赠送额度、兑换码或管理员赠送额度也会给代理商产生佣金，形成套利。

每笔符合条件的成功充值创建一个可返佣额度批次：

```text
批次可返佣总额度 = 本次实际付费购买并到账的额度
批次剩余可返佣额度 = 总额度 - 已分配消费额度 - 已退款/作废额度
```

处理规则：

- 最终消费按批次创建时间 FIFO 分配，分配多少额度就实时确认多少佣金。
- 没有可返佣额度批次时，客户仍可正常调用，但该部分消费不产生代理佣金。
- 充值退款优先取消该订单批次尚未消费的额度，不涉及佣金冲正。
- 若退款覆盖了已分配消费额度，则按原批次快照冲正对应佣金；累计冲正不得超过原批次累计佣金。
- Distributor 服务必须记录批次分配明细，确保一次消费拆分到多个折扣批次时能够逐段准确计算。

### 4.4 金额口径

| 指标 | 定义 |
|---|---|
| 累计业绩 | 归属客户最终已结算且已分配至可返佣批次的客户销售金额，扣除消费退款和冲正 |
| 累计标准消费 | 归属客户最终已结算的标准消费金额，不含预扣且扣除消费退款 |
| 累计入账佣金 | 历史所有实时确认的正向佣金，不因提现减少 |
| 待处理佣金 | 已收到但尚未完成聚合或进入异常重试的消费事件对应佣金；正常情况应接近零 |
| 可提现金额 | 已入账佣金减去已冻结提现、已支付提现和有效冲正后的余额 |
| 已提现金额 | 状态为 `paid` 的提现申请金额合计 |
| 冻结金额 | 已提交但尚未终态的提现申请占用金额 |

## 5. 关键业务流程

### 5.1 代理商开通

1. 平台管理员选择一个现有用户并创建代理商档案。
2. 配置代理商名称、状态、平台结算折扣、允许的销售折扣区间、实时返佣规则和提现规则。
3. 系统自动把该用户设为代理商主账号和 `distributor_admin` 成员。
4. Distributor 服务读取主账号已有的 `AffCode`，将该账号登记为一期邀请身份并生成代理商邀请入口。
5. 代理商首次进入后台时确认协议并补充收款信息。

同一现有用户一期只能绑定一个代理商。停用代理商后，其成员无法进入代理商后台、邀请入口停止接受新归属、未完成提现停止推进；既有客户模型调用和正常平台账号不受影响。

### 5.2 设置折扣并生成邀请入口

1. 代理商输入客户销售折扣率。
2. 系统校验其位于平台配置的允许区间内，且不低于平台结算折扣率。
3. 保存新的折扣版本和生效时间，历史版本不可修改或删除。
4. 展示邀请链接、二维码、当前折扣、复制按钮和下载二维码按钮。
5. 二维码内容必须是邀请链接本身，不嵌入账号、内部 ID、折扣公式或敏感数据。

推荐邀请链接：

```text
https://<平台域名>/distributor/invite/<公开随机码>
```

访问后由 Distributor 服务校验代理商状态，记录非敏感访问统计，再重定向至现有注册地址：

```text
https://<平台域名>/sign-up?aff=<代理商现有AffCode>
```

公开随机码必须不可枚举，不能直接使用代理商数据库自增 ID。

### 5.3 客户注册与自动绑定

1. 客户访问邀请入口，看到代理商名称和适用折扣后进入注册。
2. 邀请码传入现有邮箱注册或 OAuth 注册流程。
3. 注册事务成功写入 `users.inviter_id = 代理商操作员用户ID`。
4. Distributor 服务根据 `inviter_id` 创建唯一的代理商客户绑定，并记录注册时有效的折扣版本。
5. 客户首次登录后，在充值页看到适用的代理折扣和最终应付金额；未消费额度不产生代理佣金。

归属规则：

- 仅在首次成功注册时绑定，先注册后点击链接不自动绑定。
- 一个客户用户 ID 全局只能有一个有效代理商归属。
- 自己邀请自己、循环邀请和代理商操作员互相绑定必须被拒绝。
- 邀请链接失效、代理商停用或邀请码非法时，允许进入普通注册，但必须明确提示“本次注册不享受代理价格”。
- 重复点击不同代理商链接时，以最终提交注册请求中通过服务端校验的邀请码为准，不以纯前端 Cookie 决定。
- 已删除后重新注册、OAuth 合并账号、邮箱冲突等情况不得绕过唯一归属规则。
- 已有普通邀请关系默认不自动升级为代理归属；平台管理员可通过带审计的迁移操作处理存量用户。

兼容性说明：复用 `users.inviter_id` 可以在不修改注册核心逻辑的情况下完成“一个代理商一个当前折扣”的一期方案。若后续要求一个代理商同时拥有多个活动链接和不同折扣，必须把活动公开码传入并持久化到注册事务，不能仅依赖 Distributor 服务事后推断。

### 5.4 客户充值与返佣资格

1. 客户进入充值页，服务端识别其代理归属和当前有效折扣。
2. 服务端按平台标准价和销售折扣计算应付金额；前端展示仅用于说明，不作为结算依据。
3. 创建支付订单时写入标准额度、价格和折扣规则快照。
4. 支付渠道回调验签成功后，原有充值逻辑只为客户增加一次额度。
5. Distributor 服务以充值订单号为唯一业务键创建可返佣额度批次，此时佣金仍为零。
6. 重复支付回调不得重复充值，也不得重复建立返佣额度批次。

充值、兑换或额度增加来源必须可识别。无法确认真实付费来源的额度默认归入不可返佣额度，不能因为用户余额增加就自动建立返佣资格。

### 5.5 模型消费实时返佣

1. 现有网关完成模型请求的预扣、补扣或返还，并得到最终实际消费额度。
2. 网关写出 `billing.downstream_delta` 事实事件；事件必须包含用户 ID、Token ID、请求 ID 或任务 ID、模型、计费来源、阶段、预扣额度、差额和最终实际额度。
3. Distributor 服务忽略 `preconsume` 阶段，不在模型请求线程内同步计算佣金。
4. Distributor 服务按请求 ID 或任务 ID 聚合事件，确定截至当前的最终净消费额度。
5. 新增的净消费额度按 FIFO 分配至该客户的可返佣额度批次，并按每段批次的折扣快照计算佣金。
6. 佣金和钱包流水在同一事务落库，代理商工作台实时更新可提现金额。
7. 若后续收到负向差额、任务失败退款或账务更正，则引用原消费分配记录生成反向佣金流水。

“实时”指最终结算事件进入 outbox 后异步处理，推荐 P95 在 60 秒内展示，不要求模型响应等待 Distributor 服务。Distributor 服务不可用时模型请求照常完成，恢复后从 outbox 补算。

事件认定规则：

- `preconsume`：仅用于观测，不产生业绩或佣金。
- `settle` / `postconsume`：以事件中的 `actual_quota` 作为当前最终值，不能把 `quota_delta` 当成本次全部消费。
- `refund`：将该请求最终值调整为零并冲正已确认佣金。
- `task_recalculate`：按异步任务最新 `actual_quota` 计算与已确认值之间的差额。
- `task_failure_refund`：冲正该任务已确认的全部返佣消费。
- `billing_source=subscription`：一期默认不可返佣；`billing_source=wallet` 才进入返佣额度分配。
- 重复、乱序和迟到事件必须通过事件 ID 幂等，并按业务请求的累计最终值收敛。

### 5.6 充值退款与佣金冲正

- 全额或部分充值退款先减少原充值订单对应批次的剩余可返佣额度。
- 退款金额未覆盖已消费部分时，不冲正已确认佣金。
- 退款覆盖已分配消费额度时，从该批次最近的消费分配开始反向释放，并按原始折扣快照冲正佣金。
- 模型调用自身的退款、失败返还和异步差额调整，直接关联原请求或任务的佣金记录冲正。
- 已确认佣金尚未提现时，冲正减少可提现金额。
- 佣金已提现后发生冲正时，代理钱包形成待抵扣金额，后续佣金优先抵扣；一期不自动从代理银行卡追款。
- 所有冲正必须引用原额度批次和原消费分配，不能修改或删除原流水。

### 5.7 提现

1. 代理商维护并验证收款信息。
2. 输入提现金额，系统展示可提现金额、手续费和预计到账金额。
3. 提交时在数据库事务内校验余额，并将相应金额从可用转为冻结。
4. 平台财务审核申请，可批准或拒绝。
5. 批准后线下打款，财务录入外部流水号并确认已支付。
6. 拒绝、取消或支付失败时，冻结金额原路释放。

提现状态：

```text
submitted -> reviewing -> approved -> paid
                     |-> rejected
                     |-> cancelled
             approved -> payment_failed -> reviewing/cancelled
```

已支付提现不可删除或回退，只能通过独立财务调整单纠正。

## 6. 功能需求

### 6.1 代理商工作台

概览页至少展示：

- 可提现金额。
- 待处理佣金和异常事件数。
- 累计入账佣金。
- 累计业绩和累计标准消费。
- 已提现金额。
- 今日、本月新增客户数。
- 今日、本月模型请求数、实际消费、业绩和佣金。
- 最近佣金流水和最近提现状态。

统计卡片必须标注币种、统计时间范围和数据更新时间。

### 6.2 邀请推广

- 查看和修改当前销售折扣。
- 查看平台结算折扣及允许区间，但不得修改。
- 生成、复制、停用和重新启用邀请入口。
- 在线展示二维码并下载 PNG 图片。
- 查看访问次数、注册人数和注册转化率；一期只做基础统计，不采集跨站用户画像。
- 邀请入口停用后，历史绑定不受影响。

### 6.3 客户列表

- 展示客户用户名、脱敏邮箱、注册时间、绑定时间、状态、累计充值、累计实际消费、累计佣金贡献和最近消费时间。
- 支持按用户名/邮箱关键词、注册时间、客户状态筛选。
- 支持分页和 CSV 导出；导出属于敏感操作，必须记录审计。
- 代理商不得查看客户密码、完整 Token、平台管理备注、其他代理商信息或客户无关的系统日志。

### 6.4 业绩明细

每条业绩记录至少包含：

- 客户标识和脱敏邮箱。
- 请求 ID 或异步任务 ID、结算时间。
- 模型、端点类型、Token 名称和最终状态。
- 最终实际消费 quota 和标准消费金额。
- 关联可返佣额度批次；一次消费跨批次时可展开查看分配段。
- 每段销售折扣快照、平台结算折扣快照、客户销售金额和平台结算成本。
- 本次佣金、累计冲正金额和净佣金。
- 计费来源、结算阶段和佣金处理状态。

代理商不能看到客户请求正文、响应正文、完整 Token、渠道密钥、平台内部风控字段和其他客户的敏感信息。

### 6.5 佣金流水

流水采用不可变账本，支持以下类型：

- `commission_earned`：最终消费完成并实时确认佣金。
- `commission_reversal`：消费退款、充值退款覆盖已消费部分或纠错冲正。
- `withdrawal_freeze`：提交提现冻结。
- `withdrawal_release`：拒绝、取消或失败后解冻。
- `withdrawal_paid`：提现完成。
- `manual_adjustment`：平台财务调整，必须填写原因并双人复核。

每条流水包含业务唯一键、发生金额、发生前余额、发生后余额、关联消费/额度批次/提现单、操作人、时间和原因。

### 6.6 提现记录

- 查看提现单号、申请金额、手续费、到账金额、收款方式、状态、申请时间、审核时间、支付时间和备注。
- 支持按状态和时间筛选。
- `submitted` 状态可由代理商取消；进入 `approved` 后不可自行取消。
- 收款信息在列表中脱敏展示，历史提现保留当时的收款信息快照。

### 6.7 平台管理后台

- 代理商列表、搜索、开通、启停和详情。
- 配置结算折扣、销售折扣上下限、实时返佣规则、最低提现金额、单笔上限和手续费规则。
- 查看代理商客户、业绩、佣金账本和提现记录。
- 审核提现、录入外部支付流水号、标记支付失败。
- 发起消费佣金冲正、异常事件重放和人工财务调整。
- 查看所有敏感操作的审计记录。
- 导出代理商对账单和平台汇总报表。

## 7. Distributor 服务与现有平台边界

一期采用“旁路计算、核心写事实”的方式。Distributor 服务不参与模型请求转发和同步扣费，但现有平台需要完成三处最小集成：

1. 注册成功后提供可可靠识别的代理归属事实，或保证 Distributor 服务能通过稳定游标补齐 `inviter_id` 绑定。
2. 充值创建和成功结算时由服务端应用代理折扣，并写出包含订单快照和到账额度的幂等事件。
3. 模型最终结算、退款和异步任务差额发生时，写出 `billing.downstream_delta` 本地 outbox 事件。

这些集成不得同步调用 Distributor 服务。Distributor 服务停止只会延迟归属投影、额度批次建立和返佣展示，不得阻断注册、充值到账或模型调用。

### 7.1 复用能力

| 现有能力 | 复用方式 |
|---|---|
| 用户身份和登录 | Distributor 服务校验现有登录态，再执行自己的角色与数据范围校验 |
| `AffCode` / `InviterId` | 作为一期注册归属的权威来源 |
| 充值订单 | 建立可返佣额度批次；充值本身不产生佣金 |
| 用户额度 | 继续由现有充值结算逻辑增加 |
| Token 和模型调用 | 完全走现有平台，不经过 Distributor 服务 |
| `billing.downstream_delta` outbox 事件 | 作为实时返佣的权威事实来源，覆盖最终结算、退款和异步任务差额 |
| 消费日志 | 用于展示和对账，不单独作为佣金权威来源，避免日志开关或重复记录影响资金 |

### 7.2 Distributor 服务独立能力

- 代理商档案和成员权限。
- 折扣版本和邀请入口。
- 代理客户绑定投影。
- 可返佣额度批次、消费事件聚合和批次分配。
- 实时佣金计算、冲正和不可变钱包账本。
- 提现申请、审核和支付记录。
- 代理商报表、二维码和审计日志。

### 7.3 一致性要求

充值成功事件负责建立返佣资格，`billing.downstream_delta` 负责释放佣金。模型调用主链路只把事实写入现有本地 outbox，Distributor 服务异步消费，不能在请求线程内远程调用 Distributor 服务。

现有 upstream event dispatcher 已有自己的投递状态。代理返佣不得与 TokenOperation 共用同一个 `delivered` 标记，必须采用以下方式之一：

1. 推荐：同一事实 outbox 配置多订阅者，每个订阅者维护独立的投递游标、重试次数和 dead 状态。
2. 备选：网关在最终计费点另写一张最小化的 `distributor_commission_outbox`，仅包含返佣所需字段，由 Distributor 服务独立消费。

不能让 Distributor 服务轮询“尚未投递”的共享 outbox 行，也不能在 TokenOperation 投递完成后删除 Distributor 服务尚未确认的事实事件。

- 对充值订单号、outbox `event_id`、请求 ID/任务 ID 与结算阶段建立唯一业务约束。
- 每个消费者独立确认事件，任一消费者的成功或失败不改变其他消费者的可见性。
- 支持断点续跑、重复读取、乱序事件、迟到事件和 dead event 人工重放。
- 对同一请求保存最新已确认 `actual_quota`，新事件只按与已确认值的差额调整。
- 佣金账本事务失败时不得确认 outbox 消费成功。
- 每日执行充值批次、净消费、佣金和钱包余额四方对账。
- Distributor 服务停机期间不丢单，恢复后自动补算。

不要按 `preconsume` 返佣，不要把多条 delta 简单相加成总消费，不要直接修改现有消费日志，也不要依赖前端回调生成佣金。

## 8. 数据模型建议

| 表 | 用途 | 关键字段 |
|---|---|---|
| `distributor_accounts` | 代理商档案 | `id`, `owner_user_id`, `name`, `status`, `settlement_bps`, `min_sale_bps`, `max_sale_bps` |
| `distributor_memberships` | 代理商成员和登录授权 | `distributor_id`, `user_id`, `role`, `status` |
| `distributor_invite_identities` | 邀请身份及历史映射 | `distributor_id`, `new_api_user_id`, `status`, `effective_at`, `ended_at` |
| `distributor_discount_versions` | 折扣历史 | `distributor_id`, `sale_bps`, `effective_at`, `ended_at`, `created_by` |
| `distributor_invite_links` | 邀请入口 | `distributor_id`, `public_code`, `status`, `visit_count`, `created_at` |
| `distributor_customer_bindings` | 真实客户归属 | `distributor_id`, `customer_user_id`, `invite_link_id`, `discount_version_id`, `bound_at` |
| `distributor_quota_lots` | 可返佣额度批次 | `topup_id`, `trade_no`, `total_quota`, `allocated_quota`, `refunded_quota`, `sale_bps`, `settlement_bps`, `status` |
| `distributor_consumption_state` | 请求/任务最终消费聚合 | `business_key`, `request_id`, `task_id`, `user_id`, `actual_quota`, `billing_source`, `status`, `settled_at` |
| `distributor_consumption_allocations` | 消费到额度批次的分配 | `consumption_id`, `quota_lot_id`, `allocated_quota`, `standard_amount`, `sale_amount`, `settlement_amount` |
| `distributor_commissions` | 佣金业务记录 | `consumption_id`, `allocation_id`, `amount`, `reversed_amount`, `status`, `confirmed_at` |
| `distributor_wallet_ledger` | 不可变资金流水 | `event_id`, `distributor_id`, `type`, `amount`, `balance_before`, `balance_after`, `business_ref` |
| `distributor_withdrawals` | 提现单 | `withdrawal_no`, `distributor_id`, `amount`, `fee`, `net_amount`, `status`, `payment_ref` |
| `distributor_payout_accounts` | 收款信息 | `distributor_id`, `type`, `encrypted_detail`, `masked_detail`, `verified_at` |
| `distributor_audit_logs` | 审计 | `actor_user_id`, `distributor_id`, `action`, `object_type`, `object_id`, `before`, `after`, `request_id` |

关键约束：

- `distributor_customer_bindings.customer_user_id` 全局唯一。
- `distributor_memberships.user_id` 一期全局唯一，一个账号不能跨代理商任职。
- 当前有效的 `owner_user_id` 和 `invite_user_id` 必须指向该代理商的有效成员；历史邀请身份不能物理删除。
- `distributor_quota_lots.topup_id` 和 `trade_no` 唯一。
- `distributor_consumption_state.business_key` 唯一；每个 outbox `event_id` 只能应用一次。
- 每个额度批次满足 `allocated_quota + refunded_quota <= total_quota`。
- 每笔消费累计分配额度不得超过其最终净 `actual_quota`。
- 钱包流水 `event_id` 和业务幂等键唯一。
- 所有代理商业务表包含 `distributor_id`，代理请求的有效 `distributor_id` 只能来自服务端会话。
- 比例使用整数 BPS，金额使用 `DECIMAL` 或最小货币单位整数。
- 兼容 SQLite、MySQL 和 PostgreSQL，不依赖数据库专属 JSON 运算或部分索引。

## 10. 安全、风控与审计

- 代理商只能访问 `session.distributor_id` 范围内的数据；跨代理商对象统一返回 404。
- 登录、修改折扣、下载客户数据、修改收款信息、申请提现和审核提现需要限流。
- 修改收款信息后设置提现冷静期，推荐 24 小时。
- 提现审核人与最终确认打款人推荐分离；人工调整必须双人复核。
- 禁止代理商邀请自己、平台 Root、同一代理商成员或已归属客户。
- 检测异常高频注册、同设备批量注册、充值退款、赠送额度返佣和循环套利。
- 收款账号加密存储，列表仅返回脱敏值；日志不得记录完整账号、Token、Cookie 或支付签名。
- 邀请二维码只编码 HTTPS 链接；链接跳转需防止开放重定向。
- 所有财务状态变化、折扣变更和归属迁移保留不可删除审计记录。

## 11. 非功能需求

### 11.1 可用性

- Distributor 服务不参与模型调用，请求网关在 Distributor 服务停止时仍可正常服务。
- 财务事件消费支持重试、死信、人工重放和幂等。
- 每日自动对账，并对漏事件、重复事件、返佣批次透支、钱包余额不平和长时间待处理告警。

### 11.2 性能

- 常用列表和概览接口 P95 小于 500ms，统计型查询 P95 小于 2s。
- 邀请入口 P95 小于 300ms，生成二维码不访问外部服务。
- 报表导出改为异步任务，避免阻塞在线请求。

### 11.3 可观测性

- 每个充值批次、消费、佣金、钱包和提现事件具有统一 `request_id/event_id/business_ref`。
- 监控 outbox 投递延迟、消费返佣延迟、待处理数量、佣金入账失败、提现积压、对账差异和任务重试次数。
- 告警中不得包含完整客户邮箱、Token 或收款账号。

## 12. 验收标准

### 12.1 邀请与归属

1. 启用代理商设置合法折扣后能立即获得可复制链接和可下载二维码。
2. 链接与二维码进入同一注册流程，邮箱注册和 OAuth 注册均能正确绑定。
3. 新用户的 `inviter_id` 与 Distributor 服务客户绑定一致。
4. 同一用户不能归属两个代理商，重复事件不会创建重复绑定。
5. 无效或停用链接不会产生代理归属，也不会错误应用折扣。

### 12.2 定价与佣金

1. 客户支付金额由服务端按充值订单快照计算，篡改前端金额无效。
2. 折扣变更前后的充值分别建立对应版本的额度批次，不追溯重算。
3. 同一支付回调执行多次只充值一次、只建立一个可返佣额度批次，佣金仍为零。
4. 预扣事件不产生佣金；最终结算事件到达后 P95 60 秒内显示对应佣金。
5. 同步补扣、返还、失败退款和异步任务差额均使消费与佣金收敛到最终实际额度。
6. 同一事件重复投递或乱序到达不会重复返佣，迟到的负向事件能够准确冲正。
7. 赠送、兑换码和订阅消费默认不产生佣金；返佣额度不超过真实付费批次净额度。
8. 一笔消费跨多个折扣批次时按 FIFO 分段计算，合计与逐段结果一致。
9. 全额和部分充值退款先减少未消费批次，仅在覆盖已消费额度时冲正已产生佣金。
10. 充值批次、最终净消费、佣金记录和钱包账本能够四方对账闭合。

### 12.3 提现

1. 提现金额不能超过可提现余额，两个并发提现不能超提。
2. 提交提现后余额被正确冻结，拒绝或取消后正确释放。
3. `paid` 必须记录审核人、支付人、时间和外部流水号。
4. 代理商只能看到自己的提现，平台财务能够按权限查看和处理全量申请。

### 12.4 隔离与可靠性

1. 代理商无法通过修改 URL、查询参数或请求体访问其他代理商对象。
2. Distributor 服务停止时，已有客户模型 API 调用不受影响。
3. Distributor 服务停机后恢复，期间的充值和最终消费事件能够补算且不重复。
4. SQLite、MySQL 和 PostgreSQL 均能完成迁移和关键事务测试。

## 13. 分期建议

### 第一期：闭环 MVP

- 代理商开通和登录。
- 单一当前销售折扣。
- 邀请链接、二维码、真实用户自动归属。
- 代理客户列表。
- 充值建立可返佣额度批次。
- 最终模型消费事件实时返佣，覆盖同步、流式和异步任务。
- 失败退款、差额结算、乱序事件和充值退款冲正。
- 概览、业绩明细、佣金流水。
- 人工审核提现和基础对账。

### 第二期：运营与自动化

- 多邀请活动和活动级折扣。
- 自动支付佣金、发票与税务资料。
- 更完整的注册转化漏斗和风控。
- 定时报表、财务导出和消息通知。

### 第三期：商业扩展

- 代理专属商品或套餐。
- 自有品牌页和自定义域名。
- 经合规评审后的多级分销。

## 14. 待业务确认项

以下事项确认后才能进入详细设计和排期：

1. 平台结算折扣是每个代理商单独配置，还是全平台统一。
2. 模型消费返佣是否只覆盖钱包付费额度。本文明确建议订阅、兑换码、赠送和邀请奖励额度不返佣。
3. 同一客户同时存在付费和赠送额度时，现有平台扣款顺序能否提供可靠来源；若不能，一期采用 Distributor 服务的可返佣批次 FIFO 作为返佣上限账本。
4. 消费佣金是结算后立即可提现，还是设置统一风控冻结期。本文按立即可提现设计，充值退款通过冲正和待抵扣处理。
5. 客户注册时的折扣是永久锁定，还是每次充值使用代理商当时的当前折扣。本文推荐每次充值使用当时折扣，并固化到额度批次。
6. 已注册用户是否允许由平台管理员人工绑定；若允许，需要何种证明和审批。
7. 提现支持哪些收款方式、最低金额、单笔/日累计上限和手续费。
8. 提现是否需要实名认证、合同、发票或纳税信息。
9. 客户是否需要在注册页和充值页明确看到代理商名称。
10. 现有普通邀请奖励与代理佣金是否可以同时发放。本文推荐代理商邀请不再叠加普通邀请奖励，避免重复激励。

在以上口径未确认前，可以开发邀请归属和消费事件接入，但不建议开放真实佣金提现。
