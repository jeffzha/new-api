# Agency 授信条款与月度账单开发文档

## 1. 目标与范围

为 Agency Hub 增加完整可操作的客户授信流程：超级管理员配置客户授信额度和账期，平台按月生成上月账单并发送邮件附件，财务登记全额收款或将逾期未收款账单核销为坏账。

此功能属于 Agency Hub，不与主站普通充值发票申请混用，也不改变 `AgencyFundingDebt` 对退款、拒付或模型欠费的资金来源追踪。授信额度及账单金额沿用 Agency 的整数 quota 单位；页面和邮件必须注明是额度单位，不能仅因旧字段 `currency_code` 曾存储 `CNY` 就把 quota 解释成实际人民币金额。

## 2. 账期与金额规则

- 账单周期是上一个完整自然月，使用 `Asia/Shanghai` 时区。
- 每月 1 日生成上一周期账单；每个客户每个周期最多一张账单，依赖 `(user_id, period)` 唯一约束保证重复执行幂等。
- 所有客户的统一还款日固定为每月 1 日。周期账单在周期结束后的次月 1 日生成，到期日为其后的下一个月 1 日，给予完整一个月结算期。
- `payment_term_days` 作为账单到期后的逾期宽限天数；`overdue_at_ms = due_at_ms + payment_term_days`。超过该时点仍未结清才可转入逾期并进一步核销坏账。字段保持兼容，但 UI 使用“逾期宽限天数”说明其具体含义。
- 账单应付额度来自周期内成功的 `AgencyUsageFact.debt_quota` 汇总。零额度不生成空账单。
- 金额保持 int64 quota 单位，API 仍以整数传输。当前功能不从模型价格、实时汇率或 quota 换算系数推导人民币实收金额。
- 超过可用授信额度的新消费必须继续由 `ensureAgencyCreditAvailableTx` 拒绝；暂停授信后不得新增授信欠款，但历史账单仍需可收款、可核销。

## 3. 状态与财务操作

```text
issued -> paid
   |
   +-> overdue -> paid
          |
          +-> bad_debt
```

- 财务确认到账后可将未结清账单全额登记为已收款，必须填写支付凭证/银行流水参考号；以数据库事务锁定账单，避免与核销并发。
- 逾期前不得核销坏账。坏账核销必须填写原因，只记录当时剩余未收额度，不删除原始账单或收款信息。
- 已收款和坏账账单均不可再次收款或核销。部分收款暂不支持，首版必须明确显示该约束。
- 授信条款变更、收款、坏账核销、重发邮件都写入 Agency 审计日志，包含操作者、对象、前后状态和必要原因/凭证引用；不记录邮件正文。

## 4. 邮件账单

- 新账单默认发送到账户邮箱，附件为 UTF-8 CSV，包含发生时间、模型、接口、额度用量和业务状态。
- 邮件正文列出账期、额度、固定到期日、逾期宽限期和附件文件名；CSV 单元格需防止公式注入，HTML 邮件中的用户名必须转义。
- 邮箱缺失或邮件发送失败时将 `email_status` 记为 `failed` 并记录脱敏错误；后台每日重试失败账单。管理员可手动重发，重发成功/失败均审计。
- 邮件发送失败不能回滚已生成的账单，也不得使账单被重复创建。

## 5. API 与界面

API 位于 Agency Hub `/api/v1/root` 并要求 root 身份及 CSRF：

- `GET/PUT /users/:user_id/credit`：读取/保存额度、逾期宽限天数、状态及邮件设置；还款日固定为 1，不接受其他值。
- `GET /credit-invoices`：按客户和状态筛选账单。
- `POST /credit-invoices/:id/mark-paid`：登记全额收款及凭证引用。
- `POST /credit-invoices/:id/mark-bad-debt`：逾期账单坏账核销，要求原因。
- `POST /credit-invoices/:id/resend-email`：重发账单邮件。

前端在超级管理员全局“客户”操作中配置授信条款，在 Agency Hub 独立的“授信账单”财务页查看账单、筛选状态、登记收款、核销坏账及重发邮件。非 root 操作者不得看到全局授信和坏账管理入口。客户或代理商页面不得把授信账单误显示为主站用户充值发票。

## 6. 验收与测试

1. 上海时区的月初边界、年末和闰年均只生成上月单据，且日期计算中所有客户还款日均为每月 1 日。
2. 逾期状态在到期与宽限天数边界正确更新；未逾期不能核销坏账。
3. 重复运行账单生成、并发登记收款/坏账以及相同周期重试均不重复入账或改写终态。
4. 额度状态变更、额度上限、邮件附件内容、CSV 公式转义、无邮箱和邮件失败重试均有测试。
5. root API 必须验证身份/CSRF；收款、核销及条款变更都检查输入和写审计日志。
6. Agency Hub 迁移及相关数据访问必须按项目规则覆盖 SQLite、MySQL、PostgreSQL 的真实实例；如果测试实例不可用，结果中明确记录限制，不声称通过完整数据库兼容性验证。
7. 执行 Go 定向测试与构建、Agency Web 测试/typecheck/build、`git diff --check`。不连接生产环境、不部署。
